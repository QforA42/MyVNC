# 0.2.0-beta.16

**Date:** 2026-08-17

## Summary

"It happened again" turned out to be a real crash, not a freeze. beta.15's diagnostic logging
(added for a different, still unsolved incident) captured the actual cause directly:

```
Unhandled UI exception: System.IO.IOException: Unable to write data to the transport connection...
  at RfbClient.SendClientCutText
  at RemoteFramebufferControl.SyncLocalClipboardToRemote
  at ClipboardMonitor.WndProc
```

The connection to <hostname> dropped, and shortly afterward a clipboard sync tried to write to the
already-dead socket. `ClipboardMonitor.WndProc` (a raw Win32 window-message hook) has no try/catch
of its own around the call, so the exception propagated all the way up and killed the process.

The same vulnerability existed in `SendKeyEvent`, `SendPointerEvent`, `RequestFramebufferUpdate`
and `SendClientCutText` — all of them write directly to the stream without error handling, and
all of them can race a connection that has just died. Fixed uniformly: log and continue instead of
throwing, since the receive loop's own disconnect handling is the only authoritative signal for
"this connection is dead" — a failed outgoing write on top of that is not something the caller
can do anything about.

Also made the top-level UI exception handler actually prevent a crash (it previously logged but
never marked the exception as handled, so WPF's default behavior terminated the process anyway)
as an extra safety net against whatever happens next.

Confirmed via a follow-up question to the user: the observed "2 different desktops" were not two
simultaneous windows (no such bug was found in the log — the window count was always 0 or 1) but
just a different resolution/content after a normal close-and-reconnect cycle.
