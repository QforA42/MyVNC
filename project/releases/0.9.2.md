# 0.9.2

**Commit range:** `v0.9.1..v0.9.2` (release commit included)

**Included commits** (in git order, `v0.9.1` excluded):

2. `docs: cover wayvnc's single-client guard in the in-app Help`
3. `release: bump version to 0.9.2` (this commit)

## Summary

A pure documentation release. No client code is changed — only the help texts, in all six
languages.

The background is a real server-side failure that cost a while of debugging and that MyVNC's help
said nothing about. wayvnc has no built-in limit on the number of simultaneous clients, so anyone
who wants only one session at a time has to write a small guard themselves that listens to
`wayvncctl event-receive` and disconnects the surplus client. The most obvious implementation —
kick out the *new* connection when `connection_count > 1` — has a silent flaw: a client that
disappears without closing (network drop, sleep, a viewer that dies) leaves a half-open TCP
session behind on the server. wayvnc sets no keepalive on it, so it stays there indefinitely and
counts as client number one. Every later connection therefore becomes number two and is kicked
out immediately — the server is reachable, the port answers, the handshake starts, and the
session dies anyway, every time.

From MyVNC's point of view this looks like a client bug, which is exactly why it belongs in the
app's help. Two additions:

- **One client at a time** — a third wayvnc setup alongside external monitor and built-in screen,
  which says the guard should disconnect the *older* sessions, with the code example that does it
  (`client-list` filtered on the new client's id). A half-open session then becomes
  self-cleaning: the next connection sweeps it away instead of being blocked by it.
- **Known limitation** — the symptom description from the client side ("comes up and is kicked
  out immediately, over and over") with the diagnosis: `wayvncctl client-list` on the remote
  machine, and `wayvncctl client-disconnect <id>` on the client that is not you.

## Regression testing done for this release

- `dotnet build` (whole solution, Debug + Release) green, `dotnet test` green (42/42).
- Installer built and installed per-user (`installer\build-installer.ps1`, silent install), and
  the app verified to start from the installed binary.
- The Help page opened in the installed build via UI automation (UIAutomation against
  `HelpButton`), and the four new elements — heading, body text, code example and limitation item
  — confirmed present in the tree's text nodes. The app was running in English, so it is the
  English variant that has been seen rendered; the other five languages are verified as strings,
  not on screen. No screenshot could be taken in that session.

## Risks

None functional. The change is new text in `Loc.cs` and new `TextBlock`/`Border` elements in the
Help page's XAML; no existing strings or code paths touched. The only practical risk is that the
Help page has become longer — it already scrolls, so the layout is not affected.
