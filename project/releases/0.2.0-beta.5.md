# 0.2.0-beta.5

**Date:** 2026-08-15

## Summary

beta.4's fix (modifier state) did not solve the click-on-flyout problem when retested live — the
same symptom remained. Compared directly against TigerVNC's viewport code (`Viewport.cxx`) to find
the actual difference instead of guessing further.

TigerVNC's pointer-event handling turned out to be straightforward and essentially identical to
MyVNC's (the same RFB PointerEvent, the same "send immediately on a button change, only throttle
pure movement" principle) — so the difference was not in the protocol sequence itself. It was in
WPF's mouse-capture behavior: `RemoteFramebufferControl` subscribed to `MouseDown`/`MouseUp`
without ever calling `CaptureMouse()`. Without capture, WPF only guarantees that `MouseUp` is
routed back to the same element that received `MouseDown` if the pointer is still over the
element on release — a framebuffer redraw, or the auto-hidden tab bar animating in mid-click, can
move the hit test and silently drop the up event. The result: the server sees a button down but
never a matching button up, i.e. a "stuck" button from the compositor's point of view — a much
better explanation for "clicking a flyout does nothing" than a wlr-virtual-pointer-v1 limitation
ever was.

TigerVNC (FLTK) avoids this entirely because FLTK implicitly captures the pointer for the whole
viewport window.
