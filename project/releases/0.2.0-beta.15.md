# 0.2.0-beta.15

**Date:** 2026-08-17

## Summary

A diagnostics release, no confirmed fix.

Live incident: memory grew to 4.6 GB+ (up from the normal 150–700 MB range) while connected to
<hostname>. The log shows `<tailscale-ip>:5900` being opened via "Opening session" twice within
the same process — once at a point when beta.11's duplicate guard should have blocked the second
attempt (the first tab confirmed still connected, having just reconnected 9 seconds earlier) — yet
no "Duplicate connect blocked" line appears for either attempt.

The root cause has not been found yet. A code review of `FindActiveSession`/`OpenSession` showed
no obvious bug. Added diagnostic logging instead of guessing further:

- `FindActiveSession` now logs its candidate addresses against every currently open tab on each
  call.
- App startup always logs (regardless of the debug-logging setting) its PID and whether the
  single-instance mutex considered it the first instance — to be able to tell whether this is
  actually two separate processes running at the same time, which would explain why the duplicate
  guard (which only knows its own process's memory) never triggered.

The process was killed manually to stop the memory growth in the meantime.
