# 0.9.0

**Date:** 2026-08-21
**Commit range:** `v0.8.2..v0.9.0` (release commit included)

**Included commits** (in git order, `v0.8.2` excluded):
1. `feat: follow the Windows theme and accent color live, with a theme setting`
2. `release: bump version to 0.9.0` (this commit)

## Summary

Triggered by a readability bug reported after switching the Windows theme: headings, section
labels and page titles were barely legible. The root cause was not the color choices themselves
but half-finished theme handling — the app did read the Windows app mode at startup and chose
`Colors.Light.xaml`, but the background plate (`TerminalCanvasBackground`), the session window's
overlays and the toggle-switch knobs were painted from hard-coded dark values. The light theme's
dark text therefore ended up on an almost black background. All colors now come from the theme
palette.

The same review showed that the theme was only read at startup. Theme colors are now consumed via
`DynamicResource` instead of `StaticResource`, which lets the whole palette be swapped at runtime:
a change of the Windows app mode or accent color repaints all open windows in place — including
session windows with active RFB connections, which must not be torn down just to restyle the
chrome. `ThemeManager` listens to two independent signals: `SystemEvents` (WM_SETTINGCHANGE) and
its own watcher on the registry keys, since a value written by a script or a theming tool changes
the theme without anyone broadcasting it.

The accent color is now taken from Windows (DWM's `AccentColor`) instead of the app's own fixed
blue. Since the accent is also used as a text and icon color, it is adjusted along its HSL
lightness until it achieves 4.5:1 against the theme's card background, and text on an
accent-filled surface switches between white and near-black. The logo keeps its blue brand color,
which matches the taskbar icon.

Finally, a new option in Settings → THEME: follow Windows (default), light or dark. The accent is
taken from Windows even when the theme is pinned — the two settings are independent in Windows
itself too.

## Regression testing done for this release

- `dotnet build` (whole solution) green, `dotnet test` green (42/42).
- **Live-verified** against the running app on Windows 11 in the light system theme:
  - Dashboard and Settings legible in the light theme (the bug that triggered the release).
  - Switching the Windows app mode light → dark → light at runtime: the whole UI repaints without
    a restart.
  - The registry watcher catches an app-mode change written without a WM_SETTINGCHANGE broadcast.
  - The accent (the user's teal `#459BAC`) comes through in buttons, icons and switches, and is
    darkened to `#398090` in the light theme for contrast.
  - The setting THEME = Dark pins the dark theme while Windows is in light mode, and = Follow
    Windows reverts immediately. The choice is saved in `settings.json`.
- **Not live-verified**: re-theming a session window with an active RFB connection. The code path
  is the same as for the dashboard (the same dynamic resources, the same palette swap), but no
  live session was theme-switched during testing.

## Risks

- Moderate and broad rather than deep: `StaticResource` → `DynamicResource` touches 142
  references across all UI XAML. Lookups now happen at render time instead of at parse time, so a
  misspelled or removed resource name would show up as an invisible/unthemed control at runtime
  instead of as an error at startup. The whole UI has been reviewed visually in both themes.
- The accent color is no longer the app's own: a user with an extreme accent in Windows gets that
  color in MyVNC, albeit contrast-adjusted. Anyone who wants the fixed blue back has no option for
  that (only light/dark/follow Windows).
