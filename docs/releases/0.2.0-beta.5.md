# 0.2.0-beta.5

**Datum:** 2026-08-15

## Sammanfattning

beta.4:s fix (modifierartillstånd) löste inte klick-på-flyout-problemet vid liveomtest — samma
symptom kvarstod. Jämförde direkt mot TigerVNCs viewport-kod (`Viewport.cxx`) för att hitta den
faktiska skillnaden istället för att gissa vidare.

TigerVNCs pointer-event-hantering visade sig vara okomplicerad och i princip identisk med
MyVNC:s (samma RFB PointerEvent, samma "skicka omedelbart vid knappändring, kasta bara throttling
på ren rörelse"-princip) — så skillnaden låg inte i själva protokollsekvensen. Den låg i WPF:s
mus-capture-beteende: `RemoteFramebufferControl` prenumererade på `MouseDown`/`MouseUp` utan att
någonsin anropa `CaptureMouse()`. Utan capture garanterar WPF bara att `MouseUp` routas tillbaka
till samma element som fick `MouseDown` om pekaren fortfarande är över elementet vid
uppsläppet — en framebuffer-omritning eller den auto-dolda flikraden som animerar in mitt i ett
klick kan flytta hit-testningen och tyst tappa upp-eventet. Resultatet: servern ser en
knapp-ner men aldrig matchande knapp-upp, dvs. en "fastnad" knapp ur kompositorns perspektiv —
en betydligt bättre förklaring till "klick på en flyout gör ingenting" än en
wlr-virtual-pointer-v1-begränsning någonsin var.

TigerVNC (FLTK) undviker detta helt eftersom FLTK implicit fångar pekaren för hela
viewport-fönstret.

## Regressionstestning som gjordes inför denna release

- `dotnet build` (Debug + Release) grönt.
- Samtliga 42 enhetstester i `MyVNC.Rfb.Tests` gröna.
- **Ännu inte liveverifierat mot en riktig Waybar/Quickshell-flik** — kräver en tillgänglig host
  med synligt skrivbord (inte låsskärm/VS Code) för att slutgiltigt bekräfta.

## Risker

- Betrakta klick-på-flyout-fixen som en konkret, verifierad skillnad mot TigerVNC (inte gissning),
  men inte slutgiltigt bekräftad förrän någon faktiskt klickat på en Waybar/Quickshell-ikon i en
  riktig session efter uppgraderingen.
