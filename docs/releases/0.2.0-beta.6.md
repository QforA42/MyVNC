# 0.2.0-beta.6

**Date:** 2026-08-15

## Summary

The actual root cause behind "clicking a flyout does nothing" — confirmed via a live retest
against a real, visible Quickshell tab on <hostname>, not just code review.

Temporary logging was added to `RemoteFramebufferControl.OnMouseButton` to see exactly what was
sent on a real click. The log showed something decisive: `MouseUp` always reached the control,
but `MouseDown` never did — not once, across several click attempts. That means the server was
never told a button had gone down; every "click" only sent an `up` event with an already-cleared
button mask, which is the same as no click at all from wayvnc's/Quickshell's point of view.

A separate check (a raw RFB click via a standalone test tool, entirely without MyVNC's WPF layer)
against the same Bluetooth icon in the bar worked immediately — proving that the RFB protocol and
the wayvnc/Quickshell side were entirely innocent. The bug was in how MyVNC's WPF control
subscribed to mouse-button events: `MouseDown`/`MouseUp` (bubbling events) instead of
`PreviewMouseDown`/`PreviewMouseUp` (tunneling). Something higher up in the element tree —
suspected to be precision-touchpad-driven "manipulation" handling — was evidently consuming the
initial contact before the bubbling `MouseDown` ever got to fire, while the corresponding
`MouseUp` was still routed normally. Tunneling events are delivered top-down before that has a
chance to happen.

The two earlier fixes (beta.4: modifier state, beta.5: mouse capture) were both real, confirmed
bugs — but neither of them was this one. It took a standalone RFB test tool and detailed logging
of a real click to find the actual cause.
