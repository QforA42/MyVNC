# 0.2.0-beta.16

**Datum:** 2026-08-17

## Sammanfattning

"Det hände igen" visade sig vara en riktig krasch, inte en frysning. beta.15:s diagnostikloggning
(tillagd för en annan, fortfarande olöst incident) fångade den faktiska orsaken direkt:

```
Unhandled UI exception: System.IO.IOException: Unable to write data to the transport connection...
  at RfbClient.SendClientCutText
  at RemoteFramebufferControl.SyncLocalClipboardToRemote
  at ClipboardMonitor.WndProc
```

Anslutningen till <hostname> tappades, och strax därefter försökte en urklippssynkronisering
skriva till den redan döda socketen. `ClipboardMonitor.WndProc` (en rå Win32-fönstermeddelande-
hook) har inget eget try/catch runt anropet, så undantaget spred sig hela vägen upp och dödade
processen.

Samma sårbarhet fanns i `SendKeyEvent`, `SendPointerEvent`, `RequestFramebufferUpdate` och
`SendClientCutText` — alla skriver direkt till strömmen utan felhantering, och alla kan racea en
anslutning som just dött. Åtgärdat enhetligt: logga och fortsätt istället för att kasta, eftersom
mottagningsloopens egen frånkopplingshantering är den enda auktoritativa signalen för "den här
anslutningen är död" — ett misslyckat utgående skrivförsök ovanpå det är inte något anroparen kan
göra något åt.

Gjorde också att den översta UI-undantagshanteraren faktiskt förhindrar en krasch (den loggade
tidigare men markerade aldrig undantaget som hanterat, så WPF:s standardbeteende avslutade
processen ändå) som ett extra skyddsnät mot vad som än händer härnäst.

Bekräftat via uppföljningsfråga till användaren: den observerade "2 olika skrivbord" var inte två
samtidiga fönster (ingen sådan bugg hittades i loggen — fönsterantalet var alltid 0 eller 1) utan
bara olika upplösning/innehåll efter en normal stäng-och-återanslut-cykel.
